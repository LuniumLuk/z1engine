# Design: opt-in unity builds for macOS

## Context

- Premake 5.0.0-beta8 exposes `enableunitybuild` for VS2017+ only; the `gmake` action used on macOS has no unity support. Blob files must therefore be produced by the project (`generate`).
- Measured A/B on the reference machine (post `GLFW_INCLUDE_NONE` fix, back-to-back, both modes 0 errors / 0 warnings): runtime project 147.1 s (per-TU) vs 70.2 s (8 blobs) — 2.1x.
- The unity wall time is bounded by the heaviest blob; `python/py_engine.gen.cpp` alone takes ~75 s standalone, so it sizes the floor until that generated TU is split (out of scope).
- Prerequisites found by the experiment: `glfw_INCLUDE_NONE` mis-spelling (silently dragged Apple's `<OpenGL/gl.h>` into TUs including `glfw3.h`), five headers without `#pragma once`, and `util/string_utils.h` relied on single-inclusion semantics.

## Goals / Non-Goals

**Goals:**

- A reproducible, opt-in unity mode for macOS (`python dev/z1.py generate --unity`) that halves the clean-build time of the dominant project and is warning-free.
- Deterministic blob contents (stable ordering and naming) so `make` dependency tracking and incremental builds behave predictably.
- Keep the default (per-TU) build bit-for-bit unchanged, including its incremental speed.
- Fix the source-level issues unity exposes (macro spelling, missing include guards) rather than working around them with exclusions.

**Non-Goals:**

- Making unity the default build mode (the edit→build latency would grow from ~19 s to ~50 s).
- Unity builds on Windows/MSVC (premake can do it natively there, but it is untested here and out of scope).
- Splitting `py_engine.gen.cpp` or otherwise rebalancing the heaviest TUs; noted as a follow-up.
- Optional/unused-source analysis (`removeunused`), per-file unity exclusions beyond the vendor rule, or blob-count tuning knobs beyond a fixed target group size.

## Decisions

**D1 — Generate blobs from premake (Lua), not from the dev CLI or a shell script.**
`generate` is already the single regeneration entry point and runs premake; writing the blobs and adjusting `files`/`removefiles` in the same pass keeps project state consistent (no separate tool to remember, no stale blobs after a `generate`). Requires ~40 lines of Lua (`os.matchfiles`, `io.open`, `path.getrelative`) using the standard premake API.

**D2 — Blob layout: 8 sources per blob (target), round-robin over sorted sources, flat naming.**
Sorting + round-robin spreads the heavy TUs (`py_engine*`, `reflection_hooks`) across blobs, which keeps the wall time balanced (the measured slowest blob is 70 s vs the 147 s per-TU wall). Group count = `max(1, ceil(n / 8))`, so small projects (editor 5 TUs, game 2, bakery 4) become a single blob instead of degenerate one-source blobs. Blobs are written to `engine/intermediate/unity/<project>/<project>_unity_<k>.cpp` (gitignored, regenerated) and include their sources through relative paths, which keeps the include site's directory irrelevant.

**D3 — Vendor/implementation TUs stay standalone.**
`source/3rdparty/*.cpp` and any `*_build.cpp` (stb, tinyexr, tinygltf, tinyobjloader, imgui, `opengl_imgui_build`) define implementation macros and/or third-party loaders; combining them with regular code is what broke the first experiment (stb redefinitions, imgui OpenGL loader vs glad). They remain normal TUs (6 in runtime).

**D4 — Unity is opt-in behind `generate --unity`; the default path must not change.**
Measured incremental cost of unity: touching one source rebuilds its whole blob (~50 s observed) versus ~19 s for the per-TU build. Cold/CI builds want unity; interactive development wants per-TU. Both must stay correct, so the option flips the file lists instead of replacing them.

**D5 — Fix source-level blockers instead of excluding files.**
The `GLFW_INCLUDE_NONE` spelling fix and the five `#pragma once` additions are required for unity but are bug fixes in their own right (the GLFW typo cost ~12 % of the per-TU build time by pulling in legacy GL headers; the missing guards are a repo style violation that also risks ODR issues).

**D6 — Verification is a build/run gate, not just a compile gate.**
Unity changes cross-TU symbol resolution, so the verdict requires: 0 errors, 0 warnings, the game binary linking from blob objects, a smoke run (10 frames) with 0 GL errors, and a screenshot-parity spot check against the per-TU build.

## Risks / Trade-offs

- [Macro or symbol collisions surface later for new code] → the strict `-Wall -Wextra` baseline and the verified 0-warning unity build are the guardrails; new collisions fail the build loudly, and vendor TUs are excluded by rule.
- [Blobs go stale when files are added and the developer forgets to regenerate] → blobs are regenerated by the same `generate` step that already must run for new files to enter the build; the Makefiles reference the blob list, so a removed source disappears from the build automatically.
- [Memory: 8 blobs at -O2 on an 8 GB machine can swap] → the measured run peaked within normal limits with `-j8`; the KB documents lowering `--jobs` for unity builds on memory-constrained machines.
- [Unity masks ODR-ish differences between builds (e.g., a symbol defined differently in two TUs now errors)] → treated as the feature working; any fix belongs in the source.
- [Incremental regressions surprise users who switch modes accidentally] → unity is explicit (`--unity`), and the KB/`generate` output states the active mode.

## Migration Plan

1. Land the premake helper + option, generator passthrough, source fixes, and KB updates together.
2. Default behaviour is unchanged; rollback is a revert (blob directory is regenerated and gitignored).
3. Verification numbers recorded in `openspec/kb/build.md` next to the existing baselines.

## Open Questions

- Whether a future change should also enable premake's native unity for Windows (MSVC) — deferred until it can be validated on Windows.
- Whether splitting `py_engine.gen.cpp` is worth it once unity is in place (it sets the current 70 s floor).
