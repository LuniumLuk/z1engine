## ADDED Requirements

### Requirement: Inspector renders any reflected component without hand-written UI

The entity inspector (`engine/editor/source/type_field.cpp`) SHALL render every reflected component through the generic field UI driven by `TypeRegistry` metadata and widget hints. Hand-written per-component inspector sections for `StaticMeshComponent`, `SkeletalMeshComponent`, `CameraComponent`, and `ScriptComponent` SHALL be removed.

#### Scenario: New field appears automatically

- **WHEN** a developer adds a reflected field with `FF_Default` to any component
- **THEN** it shows up in the inspector with the widget selected by its type and widget-hint string
- **AND** no editor source file was edited

#### Scenario: Read-only and hidden flags honored

- **WHEN** a field is declared `FF_ReadOnly` or `FF_Hidden`
- **THEN** the inspector renders it disabled or not at all, respectively

---

### Requirement: Generalized asset-reference widget

Any reflected asset-reference field SHALL render as a drag-drop asset slot accepting `ASSET_ITEM` payloads of the matching asset type, replacing today's per-type special cases.

#### Scenario: Assign mesh via drag-drop

- **WHEN** a user drags a `StaticMesh` asset onto the mesh slot of a `StaticMeshComponent`
- **THEN** the field is assigned and the change is visible in the viewport

#### Scenario: Wrong asset type rejected

- **WHEN** a user drags an asset of a different type onto the slot
- **THEN** the payload is not accepted and the field is unchanged

---

### Requirement: Registry-driven add/remove component menu

The add/remove-component menu in `engine/editor/source/editor_layer.cpp` SHALL be generated by enumerating `TypeRegistry` for types carrying component hooks.

#### Scenario: Menu lists all components

- **WHEN** a user opens the add-component context menu on an entity
- **THEN** every registered component type is listed
- **AND** selecting one attaches it via its registry hook with default values

---

### Requirement: Script entry editing

The inspector SHALL display and edit `ScriptComponent` script entries (module and class name) through reflection metadata.

#### Scenario: Edit script class name

- **WHEN** a user edits the module or class string of a script entry
- **THEN** the change persists to scene YAML through the reflection-driven serializer

---

### Requirement: Reflection-driven material inspector

The material editor UI SHALL be driven by reflected `Material` / `MaterialInstance` variable metadata: variable list, `DataType`-typed value widgets, texture slots, and override flags.

#### Scenario: Edit a material instance override

- **WHEN** a user changes an overridden variable value on a `MaterialInstance`
- **THEN** the value round-trips through reflection and is saved into the material instance YAML

#### Scenario: Guid fields displayed read-only

- **WHEN** an inspector shows a `Guid` field (e.g. `TagComponent::m_id`)
- **THEN** it renders as read-only text
